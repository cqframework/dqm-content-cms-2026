# ClaimElementsTests test cases

Test data for the `ClaimElementsTests` CQL library, evaluated by the CQL VS Code extension
(`CQL: Execute`). Each subfolder is one patient context (**`Patient.id` must equal the folder
name**); results are written to [../results/ClaimElementsTests.txt](../results/ClaimElementsTests.txt).

Every test expression is evaluated for every case. A case test lists its expected result for
each case it covers and is `true` for the others, and invariant tests (marked in the library)
must hold for every case. So every test must be `true` for every case:

- `true`: passed (or the test doesn't cover this case)
- `false`: failed
- `null`: failed; the assertion couldn't be evaluated, e.g. because an element it reads came
  back null

To check a run, including that every case name used in the tests is one of the case folders:

```
python .claude/skills/cql/check_results.py ClaimElementsTests
```

The data was generated by a script, but the JSON files are the source of truth; edit them
directly.

## Coding

All claims carry the US Quality Core Claim profile, a `use` of `claim` unless noted, and the
required `created`, `provider`, `priority`, and `insurance` elements (the provider and coverage
references don't resolve, and nothing reads them).

| Element | System | Codes |
|---------|--------|-------|
| `diagnosis.diagnosisCodeableConcept` | ICD-10-CM | `I21.4`, `E11.9`, `I10`, `J18.9` |
| `diagnosis.type` | `ex-diagnosistype` | `principal`, `admitting` |
| `diagnosis.onAdmission` | CMS present on admission | `Y`, `N` |
| `procedure.procedureCodeableConcept` | ICD-10-PCS | `02703ZZ`, `B2111ZZ`, `0DTJ4ZZ` |
| `procedure.type` | `ex-procedure-type` | `primary`, `secondary` |
| `item.productOrService` | CPT | `99223`, `93458`, `99213`, `99214`, `36415`, `99232` |

All times are UTC. Resource ids carry the case number (`clm-01`, `enc-02a`, ...). Rows are
identified in the tests by `claim:item` or `claim:item:diagnosis` (or `:procedure`) sequence keys.

## Observations for review

1. **`Claim Encounter Item` paired every item with every encounter on the claim — fixed.** The
   expression used `let item: C.item, encounter: item.encounter` and then
   `from item I, encounter E`. The sources of a multi-source query are independent, so that is
   the cross product of all the claim's items with all the encounters any of them reference:
   case 02 gave six rows (three items by two encounters, including item 3, which references no
   encounter) instead of two. Case 01 hid this, because both its items reference the same
   encounter and the query's implicit distinct removed the duplicate rows. The expression now
   unfolds the encounters in a query nested in the item query.
2. **A serviced date on the encounter's first day gives an unknown result.**
   `toServicedInterval()` turns a date into a day-precision interval, and comparing that with an encounter start that
   has a time is uncertain at day precision, so `during` is null (case 04, `clm-04d`). A
   serviced date strictly inside the encounter (`clm-04e`) works. The date is converted with
   the timezone offset of the evaluation, so `enc-04` starts at 12:00 UTC, which is on 04-01
   in every timezone; with an earlier start the result for `clm-04d` would depend on where
   the tests are run.
   `TestIsRelatedToServicedDateOnStartDay` asserts the null; whether a same-day serviced date
   should count as related is a design question.
3. **`isRelatedTo()` returns null when the relationship can't be established (by design).**
   It is `references or serviced during period or billablePeriod during period`, which is
   false only when every part is false. The reference test is never null (an item with no
   encounter references gives false), but either date test is null when its interval is
   missing (no serviced element, no `billablePeriod`, or an encounter with no `period`) or
   can't be compared at day precision (observation 2). So when the reference doesn't match and
   nothing else is true, an unknown date test makes the result null, and as with any CQL
   conditional the unknown is propagated: `not isRelatedTo(...)` is null too. A true part
   still makes the result true. Cases 02 (no serviced element) and 04 (`clm-04f` and
   `clm-04g`, no billable period) cover this.
4. **`Claim Diagnosis` and `Claim Procedure` retrieved `[Claim]`, unqualified — fixed.** All
   four retrieves are now `[USQualityCore.Claim]`. The library header records that on promotion
   to the Using CQL with FHIR IG it would be generalized to `[FHIR.Claim]`.
5. **`isRelatedTo()` is only defined for `Claim Item Diagnosis` rows,** not for
   `Claim Item Procedure` rows.
6. **Serviced dates came back null — fixed.** ClaimCommon's conversion of `serviced` was an
   overload of `toInterval()`, and ClaimElements includes FHIRCommon too. FHIRCommon 2.0.0's
   `toInterval()` returns null for a `FHIR.date`, and the call in ClaimElements behaved as if it
   resolved to that definition: every serviced date was null, with no ambiguity error, while
   serviced periods (which both definitions handle) worked. The ClaimCommon function is now
   `toServicedInterval()`.
